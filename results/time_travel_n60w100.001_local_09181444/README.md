# time_travel.py / n60w100.001 — シードを振った 10 回実行（ローカル、2026-09-18）

`src/time_travel.py`（時間展開型・総移動時間最小化）を、時間枠が広い
`n60w100.001`（顧客 60・幅 w100）で**同条件・シードのみ変更**して 10 回実行した記録。
「制限時間を延ばすよりシードを振る方が効く」という
[n200w20.001 の記録](../time_travel_n200w20.001_local_09172357/README.md) の結論を、
別系統のインスタンス（顧客数は少ないが項数は 9 倍）で確かめるのが狙い。

- 実行環境: ローカル（CPU 28 コア、GPU なし。ABS3Solver は約 1560% CPU）
- モデル規模: **7,366 変数**（x 5,555 + b 1,811）/ **2,504,029 項**、構築 1.6〜1.9 秒、RSS 1.1 GB
  （比較: n200w20.001 は 5,660 変数 / 280,748 項。顧客数は 1/3 でも項数は 9 倍。
  w100 は時間枠が広く `b` の定義域 `[arr, E-1]` が縮まないため）
- 既知最適 travel = **515**（`instances/Dumas/Dumas-best-known-traveltime.txt`）
- 制限時間はすべて 300 秒

|---|---|---|---|---|---|
| `seed03_300s.log` | 3 | **520** | **0** | True | 最良。既知最適比 +5（+0.97%） |
| `seed05_300s.log` | 5 | 531 | 0 | True | 完全実行可能 |
| `seed02_300s.log` | 2 | 536 | 1 (conflict) | True | |
| `seed07_300s.log` | 7 | 536 | 1 (conflict) | True | |
| `seed10_300s.log` | 10 | 537 | 1 (conflict) | True | |
| `seed06_300s.log` | 6 | 538 | 1 (conflict) | True | |
| `seed08_300s.log` | 8 | 542 | 1 (conflict) | True | |
| `seed01_300s.log` | 1 | 545 | 1 (conflict) | True | |
| `seed09_300s.log` | 9 | 547 | 1 (conflict) | True | |
| `seed04_300s.log` | 4 | (484) | 1 (once) | **False** | 顧客 1 つ未訪問（59/60）。travel は無効 |

`feasible` 列は復元したツアーを最早開始で再シミュレートした独立検算
（時間枠・期限をすべて満たすか）。`QUBO 制約違反` は QUBO 側の `violated cons`。

## 読み取れること

- **シードの効き方が大きい**。実行可能 9 本の travel は 520〜547 で、幅は 27（5.2%）。
  同一条件・同一時間で 5% ぶれるので、1 回の実行値でモデルを評価してはいけない。
- **`violated cons = 0` に入れた run だけが上位**。10 本中 2 本（seed 3, 5）だけが
  ペナルティ項ゼロに到達し、その 2 本がそのまま travel でも 1 位・2 位。
  残り 8 本は `conflict_constr = 1` を抱えたまま終わっており、n200w20.001 と同じ
  「実行可能領域に入りきれていないのが敗因」というパターンが再現した。
  なお conflict を 1 本破った run は objective が travel より 30〜50 小さく出る
  （制約を破って得をしている）ので、**objective ではなく travel を見ること**。
- **モデル自体は厳密で、最適解は表現できている**。既知最適ツアー（travel 515）を
  代入すると、x はすべて定義域内、衝突・同一頂点・連続性の違反ゼロ、
  真の待ち 67 がすべて `b` の定義域に収まり objective = 582 − 67 = **515 ちょうど**。
  三角不等式違反による誤差はこのインスタンスでは出ない。
  したがって 520 と 515 の差 5 は**モデルの限界ではなく探索の限界**。
- **`b` が埋まりきっていない**。seed 3 の解はログ上 objective = 525 だが、同じツアーで
  `b` を定義域いっぱいまで 1 にすれば 520（= travel と一致）になる。seed 5 も 537 → 531。
  `sum(b)` は最大化方向なので理屈の上では自然に埋まるはずだが、実際には 5〜6 単位
  取りこぼしたまま止まっている。エネルギー地形の平坦さの現れで、
  後処理で `b` を貪欲に飽和させるだけで目的関数値が 1% 改善する余地がある。
